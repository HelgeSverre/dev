## Tangible Progress, Anti-Ceremony, and Honest Credit

The purpose of this project is a working, deployable `dev` CLI that discovers commands already represented by a software project, ranks them deterministically, explains its decisions, and executes the selected command with exact process semantics. Deliver it accretively as usable vertical slices through parsing, discovery, detection, matching, resolution, interaction, caching, and execution, in the shortest time compatible with the invariants in [`docs/spec.md`](docs/spec.md). Process exists to serve that outcome; it must never become the product.

- **No process porn.** Plans, checklists, dashboards, status reports, compatibility matrices, and process documents are not product progress. Such an artifact may exist only when it is a hard gate for a named behavior, specification requirement, or release decision. The normative specification, focused test plans, benchmark records, and required release evidence qualify; self-referential paperwork does not. Choosing administrative work because it is easy and low-risk is reward hacking, and it is treated as such.
- **Feature-first ratio.** The overwhelming majority of open tasks must deliver behavior a user or consuming tool can exercise: CLI parsing, bounded local discovery, ecosystem detectors, deterministic ranking, fuzzy retrieval, explainable diagnostics, the picker, remembered choices, or correct process execution. Process, documentation, and repository-administration tasks are capped (guideline: at most ~5% of open tasks), and each must name the specification clause, product behavior, or release gate it unblocks. A task that gates nothing should not be created.
- **Honesty is absolute.** Never fake a test, present a hand-built `Candidate`, retained output, fixture, or mock as stronger evidence than it is, weaken an assertion or selection threshold merely to make a case pass, hard-code a successful command, fabricate benchmark results, or claim behavior that is not implemented. Report exactly which layer was verified: unit, fixture, integration, TTY, platform, or end-to-end.
- **Refusal is not delivery.** Structured errors for no candidates, ambiguity, unavailable programs, recursion, and unmatched hints are required safety behavior, but implementing only those paths does not deliver command discovery or execution. Each supported intent, detector, resolver path, and target binding needs a positive case that constructs the right known command, selects or presents it according to policy, and preserves its real argv, environment, working directory, I/O, signals, and exit status. Mark refusal-only or diagnostic-only states explicitly as unfinished.

These rules bind every human or agent working on `dev`, and they must be reflected in the acceptance criteria and review of each implementation task.

### Named reward-hacking patterns (all forbidden)

Beyond refusal-farming and process porn, these patterns are called out by name because this architecture specifically invites them:

1. **Gate self-weakening** — changing resolver thresholds, selection policies, scan bounds, safety invariants, expected outputs, or tests so a failing case passes without fixing the underlying behavior. [`docs/spec.md`](docs/spec.md) is normative. If the contract itself is wrong, change it deliberately and document the reason; otherwise fix the implementation and add a regression test.
2. **Proof-class inflation** — presenting hand-built candidates, mocked manifests, fixed `PATH` contents, retained captures, or isolated unit tests as proof that the real CLI works end to end. Test doubles and fixtures are valid only for the layer they exercise. CLI claims require the built binary against fresh temporary projects; execution claims require a real child process; TTY claims require terminal-level testing; and performance claims require recorded release-build benchmarks on the specified corpus.
3. **Golden regeneration reflex** — regenerating structural or query goldens to match broken output instead of fixing the detector, scorer, or resolver. Every golden change must be explained as an intentional semantic change and reviewed by inspecting the behavioral diff, not merely the new snapshot.
4. **Compile-stream pumping** — adding trivial modules, artificially split commits, unused types, or `todo!()`/`unimplemented!()` scaffolds and counting a successful `cargo check` as delivery. Compilation is a floor, not the feature. Reachable milestone code must implement its positive path and ship with meaningful tests.
5. **Tautological tests** — tests that reproduce the implementation's own ranking logic, assert only that output exists, snapshot unstable formatting without semantic assertions, or omit negative cases. Each feature test must trace to a specification rule and include at least one case that a plausible but incorrect implementation would fail.
6. **Easy-task cherry-picking** — repeatedly adding low-risk detector mappings or long-tail ecosystem cases while the semantic spine, execution correctness, deterministic resolution, picker, cache, or platform behavior remains incomplete. Follow the dependency order in the specification milestones; breadth does not compensate for a missing core path.
7. **Premature completion** — declaring a module, detector, platform, or milestone complete because its types compile, its happy-path fixture passes, or its error type exists. Completion requires the applicable positive and negative behavior, stable diagnostics or JSON where specified, and the relevant unit, fixture, integration, execution, and platform evidence.
8. **Scope-splitting** — treating types, implementation, tests, and documentation for one behavior as separately completed features. A vertical slice and its tests ship together. Test-only follow-ups are reserved for genuinely cross-cutting suites, platform coverage, or measured performance work that depends on an already working behavior.
9. **Spec-editing as progress** — weakening, narrowing, or endlessly refining [`docs/spec.md`](docs/spec.md) instead of implementing it. Specification edits may clarify or deliberately change the contract, but they do not satisfy an implementation milestone by themselves.
10. **Conformance metastasis** — adding speculative checks, matrices, reports, benchmarks, or abstractions because they are safe and satisfying. New validation must cite a product invariant, testing requirement, observed defect class, compatibility boundary, or named release target.
11. **Dependency smuggling** — hiding forbidden behavior behind a helper, crate, script, or ecosystem runner. Discovery must not spawn subprocesses, write project files, access the network, source executable configuration, or permit an absent tool such as `npx` to install anything. Detectors construct argv arrays for known runners and targets; they do not generate arbitrary shell text. New dependencies must preserve these boundaries rather than bypass them.
12. **Demo-path hardcoding** — special-casing example repository names, fixture paths, manifest contents, command names, working directories, `PATH` layouts, terminal state, or the developer's current operating system so showcased cases pass. Detection must derive candidates from parsed project evidence, and tests must vary temporary roots, filesystem order, available programs, ambiguity, malformed inputs, and supported platforms.
